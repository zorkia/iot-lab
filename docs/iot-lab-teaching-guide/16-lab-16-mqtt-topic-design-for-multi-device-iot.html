LAB 16 - MQTT Topic Design for Multi-device IoT

ก่อนหน้า: LAB 15 - Automatic Controlกลับหน้าแรกถัดไป: LAB 17 - Multi-device Dashboard

16.1 แนวคิดของ LAB

LAB 01-15 ใช้ MQTT Topic แบบง่าย เช่น:

pkru/iot/001/data
pkru/iot/001/cmd

เมื่อระบบมีอุปกรณ์เพียงตัวเดียว Topic ลักษณะนี้ยังใช้งานได้ แต่ระบบ IoT จริงมักมีหลาย Device เช่น:

ESP32-001
ESP32-002
ESP32-003
...
ESP32-100

ถ้าไม่มีการออกแบบ Topic ที่ดี ระบบจะเริ่มมีปัญหา:

  • แยก Device ยาก
  • Subscribe ข้อมูลหลาย Device ยาก
  • แยก Data / Status / Command ไม่ชัดเจน
  • Node-RED Flow ซับซ้อน
  • เพิ่ม Device ใหม่ได้ยาก
  • กำหนด MQTT Permission ในอนาคตได้ยาก

ดังนั้น LAB นี้จะเปลี่ยนจาก:

Single-device MQTT

ไปสู่:

Structured Multi-device MQTT

แนวคิดหลักคือ:

MQTT Topic = Address ของข้อมูลในระบบ IoT

16.2 วัตถุประสงค์

หลังจบ LAB นี้ คุณจะสามารถ:

  • อธิบาย MQTT Topic Hierarchy
  • ออกแบบ Topic สำหรับหลาย Device
  • แยก Data, Status และ Command Topic
  • ใช้ Device ID ใน Topic
  • ใช้ Single-level Wildcard +
  • ใช้ Multi-level Wildcard #
  • Subscribe ข้อมูลจากหลาย Device
  • ใช้ Node-RED รับข้อมูลจากหลาย Device
  • แยก Device ID จาก msg.topic
  • เข้าใจพื้นฐานของ Scalable MQTT Architecture

16.3 ปัญหาของ Single-device Design

สมมติระบบเดิมมี:

pkru/iot/001/data
pkru/iot/001/cmd

เมื่อเพิ่ม Device ใหม่อาจสร้าง:

pkru/iot/002/data
pkru/iot/002/cmd

pkru/iot/003/data
pkru/iot/003/cmd

โครงสร้างนี้ยังใช้งานได้ แต่ต้องกำหนดมาตรฐานให้ชัดเจนตั้งแต่ต้น Topic ที่ดีควรตอบได้ว่า:

ข้อมูลมาจากระบบใด?
มาจาก Device ใด?
เป็นข้อมูลประเภทใด?

กำหนดโครงสร้างหลัก:

16.10 Subscribe แบบระบุ Device

ต้องการดูเฉพาะ Device 001:

mosquitto_sub -h localhost \
  -t "pkru/iot/001/data" \
  -v

จะได้รับเฉพาะ:

pkru/iot/001/data

ข้อมูลจาก Device 002 และ 003 จะไม่ถูกส่งมายัง Subscriber นี้

16.11 MQTT Single-level Wildcard +

เครื่องหมาย:

+

แทน Topic Level ได้หนึ่งระดับ ตัวอย่าง:

pkru/iot/+/data

หมายถึง:

pkru/iot/001/data
pkru/iot/002/data
pkru/iot/003/data
pkru/iot/004/data
...

ใช้คำสั่ง:

mosquitto_sub -h localhost \
  -t "pkru/iot/+/data" \
  -v

จากนั้นส่ง:

mosquitto_pub -h localhost \
  -t "pkru/iot/001/data" \
  -m '{"temp":30,"humi":70,"light":1000}'

mosquitto_pub -h localhost \
  -t "pkru/iot/002/data" \
  -m '{"temp":32,"humi":75,"light":1500}'

mosquitto_pub -h localhost \
  -t "pkru/iot/003/data" \
  -m '{"temp":35,"humi":80,"light":2000}'

ผล:

pkru/iot/001/data {"temp":30,"humi":70,"light":1000}
pkru/iot/002/data {"temp":32,"humi":75,"light":1500}
pkru/iot/003/data {"temp":35,"humi":80,"light":2000}

นี่เป็นแนวคิดสำคัญมากสำหรับ Multi-device MQTT

Subscriber ไม่จำเป็นต้องสร้าง Subscription แยกทุก Device

16.12 ความหมายของ +

Topic:

pkru/iot/+/data

แบ่งเป็น:

pkru
 │
iot
 │
 +
 │
data

+ แทนได้หนึ่ง Topic Level ดังนั้นตรงกับ:

pkru/iot/001/data
pkru/iot/abc/data

แต่ไม่ตรงกับ:

pkru/iot/001/status
pkru/iot/site1/001/data

เพราะจำนวน Topic Level ไม่ตรงกัน

16.13 MQTT Multi-level Wildcard #

เครื่องหมาย:

#

ใช้แทน Topic ตั้งแต่ระดับตำแหน่งนั้นลงไปทั้งหมด ตัวอย่าง:

pkru/iot/#

ใช้คำสั่ง:

mosquitto_sub -h localhost \
  -t "pkru/iot/#" \
  -v

จะสามารถรับ:

pkru/iot/001/data
pkru/iot/001/status
pkru/iot/001/cmd

pkru/iot/002/data
pkru/iot/002/status
pkru/iot/002/cmd

รวมถึง Topic ที่มีระดับย่อยเพิ่มเติมภายใต้:

pkru/iot/

16.14 ทดลอง #

เปิด:

mosquitto_sub -h localhost \
  -t "pkru/iot/#" \
  -v

จากนั้นส่ง:

mosquitto_pub -h localhost \
  -t "pkru/iot/001/data" \
  -m '{"temp":30}'

ส่ง Status:

mosquitto_pub -h localhost \
  -t "pkru/iot/001/status" \
  -m "ONLINE"

ส่ง Command:

mosquitto_pub -h localhost \
  -t "pkru/iot/001/cmd" \
  -m "ON"

Subscriber จะเห็นทั้งหมด:

pkru/iot/001/data {"temp":30}
pkru/iot/001/status ONLINE
pkru/iot/001/cmd ON

16.15 เปรียบเทียบ + และ #

+

แทนหนึ่ง Topic Level:

pkru/iot/+/data

เหมาะสำหรับ:

รับ data ของทุก Device

#

แทนทุก Topic Level ตั้งแต่ตำแหน่งนั้นลงไป:

pkru/iot/#

เหมาะสำหรับ:

Debug
Monitoring
ตรวจสอบ MQTT Traffic ของระบบ

ไม่ควรใช้ # โดยไม่จำเป็นใน Application จริง หาก Application ต้องการข้อมูลเพียงบางประเภท หลักการคือ:

Subscribe เฉพาะข้อมูลที่ Application ต้องใช้

16.16 Node-RED Multi-device MQTT Input

ใน Node-RED สร้าง:

[MQTT In]
    │
    ▼
  [JSON]
    │
    ▼
  [Debug]

ตั้ง MQTT In Topic:

pkru/iot/+/data

Broker:

localhost:1883

เมื่อ Device หลายตัวส่งข้อมูล:

ESP32-001 ─┐
ESP32-002 ─┼──→ MQTT ──→ Node-RED
ESP32-003 ─┘

Node-RED ใช้ MQTT In เพียง Node เดียวรับข้อมูลได้ทุก Device

16.17 msg.topic

เมื่อ Node-RED รับ MQTT Message ตัวอย่าง:

Topic:
pkru/iot/002/data

Payload:
{"temp":32,"humi":75,"light":1500}

Node-RED จะมี:

msg.topic

เท่ากับ:

pkru/iot/002/data

ดังนั้น Topic ไม่ได้ใช้แค่ Routing แต่ยังสามารถใช้ระบุ Source ของข้อมูลได้ด้วย

16.18 แยก Device ID จาก Topic

เพิ่ม Function Node ชื่อ:

Extract Device ID

ใช้:

let parts = msg.topic.split("/");

msg.device_id = parts[2];

return msg;

ตัวอย่าง msg.topic คือ:

pkru/iot/002/data

เมื่อ:

split("/")

จะได้:

parts[0] = pkru
parts[1] = iot
parts[2] = 002
parts[3] = data

ดังนั้น:

msg.device_id = "002"

16.19 ตรวจสอบ Device ID

Flow:

[MQTT In]
     │
     ▼
   [JSON]
     │
     ▼
[Extract Device ID]
     │
     ▼
   [Debug]

เมื่อรับ:

pkru/iot/003/data

Node-RED จะได้:

msg.device_id = "003"

และ:

msg.payload.temp
msg.payload.humi
msg.payload.light

ทำให้ Processing Layer รู้ทั้ง:

ข้อมูลคืออะไร
ข้อมูลมาจาก Device ใด

16.20 แยก Device ด้วย Switch Node

สามารถใช้:

msg.device_id

ใน Switch Node Flow:

                      ┌── 001 ──→ Device 001
                      │
MQTT → Extract ID ────┼── 002 ──→ Device 002
                      │
                      └── 003 ──→ Device 003

ตั้ง Switch Property:

msg.device_id

Rules:

== 001
== 002
== 003

วิธีนี้เหมาะสำหรับการทดลองให้เห็น Routing แต่เมื่อมี Device จำนวนมาก ไม่ควรสร้าง Output แยกทีละ Device เพราะจะทำให้ Flow ไม่สามารถ Scale ได้ดี

16.21 หลักการ Scalable Processing

ระบบขนาดเล็กอาจทำ:

Device 001 → Flow 001
Device 002 → Flow 002
Device 003 → Flow 003

แต่ถ้ามี 100 Device:

Device 001 → Flow 001
Device 002 → Flow 002
...
Device 100 → Flow 100

จะดูแลยากมาก แนวทางที่ดีกว่าคือ:

All Devices
     ↓
pkru/iot/+/data
     ↓
Common Processing
     ↓
Extract Device ID
     ↓
Process by device_id

หรือ:

ESP32-001 ─┐
ESP32-002 ─┤
ESP32-003 ─┼──→ MQTT
ESP32-004 ─┤       │
   ...     │       ▼
ESP32-100 ─┘   Node-RED
                   │
                   ▼
            Common Processing

นี่คือพื้นฐานของ Scalable Multi-device Architecture

16.22 จำลองหลาย Device อัตโนมัติ

สามารถใช้ Raspberry Pi จำลอง ESP32 จำนวน 3 ตัว ใช้ Terminal หรือสร้าง Script:

while true
do
    temp1=$((25 + RANDOM % 11))
    temp2=$((25 + RANDOM % 11))
    temp3=$((25 + RANDOM % 11))

    mosquitto_pub \
        -h localhost \
        -t "pkru/iot/001/data" \
        -m "{\"temp\":$temp1,\"humi\":70,\"light\":1000}"

    mosquitto_pub \
        -h localhost \
        -t "pkru/iot/002/data" \
        -m "{\"temp\":$temp2,\"humi\":75,\"light\":1500}"

    mosquitto_pub \
        -h localhost \
        -t "pkru/iot/003/data" \
        -m "{\"temp\":$temp3,\"humi\":80,\"light\":2000}"

    sleep 2
done

เปิดอีก Terminal:

mosquitto_sub -h localhost \
  -t "pkru/iot/+/data" \
  -v

จะเห็นข้อมูลจาก Device ทั้งสาม

16.23 ส่ง Command ไป Device เฉพาะตัว

ต้องการเปิด Actuator ของ Device 001:

mosquitto_pub -h localhost \
  -t "pkru/iot/001/cmd" \
  -m "ON"

Device 001 Subscribe:

pkru/iot/001/cmd

จึงได้รับคำสั่ง แต่ Device 002 Subscribe:

pkru/iot/002/cmd

จะไม่ได้รับคำสั่งนี้ ทำให้สามารถควบคุม Device แต่ละตัวแยกกันได้

16.24 Device-side Subscription

แต่ละ ESP32 ควร Subscribe เฉพาะ Command ของตัวเอง ESP32-001:

pkru/iot/001/cmd

ESP32-002:

pkru/iot/002/cmd

ESP32-003:

pkru/iot/003/cmd

ไม่ควรให้ทุก ESP32 Subscribe:

pkru/iot/+/cmd

โดยไม่มีเหตุผล เพราะแต่ละ Device ไม่จำเป็นต้องรับ Command ของ Device อื่น หลักการคือ:

Publish only what is necessary
Subscribe only what is necessary

16.25 Device ID ต้องไม่ซ้ำ

ในระบบ Multi-device:

device_id

ต้องระบุ Device ได้อย่างไม่กำกวมภายในระบบที่ออกแบบ ตัวอย่าง:

001
002
003

ห้ามมี ESP32 สองตัวใช้:

pkru/iot/001/data

โดยไม่ตั้งใจ เพราะ Gateway จะไม่สามารถแยกได้ว่าข้อมูลมาจาก Device ใด สำหรับ LAB ใช้เลข:

001
002
003

เพื่อให้อ่านง่าย ระบบจริงอาจใช้:

esp01
room101
greenhouse01
meter01

ตามมาตรฐานของระบบ

16.26 Topic Naming Rules

ควรกำหนดมาตรฐาน Topic ตั้งแต่ต้น แนะนำ:

lowercase

เช่น:

pkru/iot/001/data

หลีกเลี่ยง:

PKRU/IoT/001/Data

เพราะ MQTT Topic เป็น Case-sensitive ดังนั้น:

pkru/iot/001/data
PKRU/IOT/001/DATA

เป็นคนละ Topic ไม่ควรใช้ Space หลีกเลี่ยง:

pkru/iot/device 001/data

ใช้:

pkru/iot/001/data

ชื่อควรสั้นแต่สื่อความหมาย ดี:

pkru/iot/001/status

ไม่ควรยาวโดยไม่มีประโยชน์ เช่น:

pkru/internet_of_things/device_number_001/device_status_information

16.27 Topic กับ Payload มีหน้าที่ต่างกัน

ไม่ควรใส่ข้อมูลทุกอย่างลงใน Topic ตัวอย่างที่ไม่เหมาะสำหรับ LAB นี้:

pkru/iot/001/temp/32/humi/70/light/1500

เพราะค่าของ Sensor เปลี่ยนตลอดเวลาและควรอยู่ใน Payload แนวทางที่เหมาะสม Topic:

pkru/iot/001/data

Payload:

{
  "temp": 32,
  "humi": 70,
  "light": 1500
}

หลักการคือ:

Topic
  ↓
ใช้ระบุเส้นทาง / ประเภท / Source

Payload
  ↓
ใช้เก็บข้อมูล

16.28 Topic ไม่ใช่ Folder จริง

แม้ Topic:

pkru/iot/001/data

จะดูเหมือน Directory:

pkru
  └── iot
       └── 001
            └── data

แต่ MQTT Broker ไม่ได้สร้าง Folder จริง เครื่องหมาย:

/

เป็นเพียง Topic Level Separator ใช้สร้าง Logical Hierarchy

16.29 ระวัง Leading Slash

ควรใช้:

pkru/iot/001/data

ไม่ควรใช้:

/pkru/iot/001/data

เพราะ Leading Slash จะสร้าง Topic Level ว่างขึ้นมาอีกหนึ่งระดับ และทำให้ Topic Structure ไม่สม่ำเสมอ

16.30 Wildcard ใช้กับ Subscription

Wildcard:

+
#

ใช้สำหรับ Topic Filter ตอน Subscribe ตัวอย่าง:

mosquitto_sub -h localhost \
  -t "pkru/iot/+/data"

หรือ:

mosquitto_sub -h localhost \
  -t "pkru/iot/#"

ไม่ใช้ Wildcard เพื่อ Publish ข้อมูลไปยังหลาย Topic ตัวอย่างนี้ไม่ใช่วิธี Publish ที่ถูกต้อง:

mosquitto_pub \
  -t "pkru/iot/+/cmd" \
  -m "ON"

ถ้าต้องการส่ง Command ให้ Device หลายตัว ควรออกแบบ Broadcast / Group Topic โดยตั้งใจ ซึ่งยังไม่จำเป็นใน LAB นี้
