28.10 ตัวอย่าง Automatic Control

ตัวอย่างการควบคุมอุณหภูมิ:

temp > 35
    → FAN ON
temp < 30
    → FAN OFF
30 ≤ temp ≤ 35
    → KEEP PREVIOUS STATE

เงื่อนไขนี้เป็น Hysteresis ซึ่งช่วยลดการสลับสถานะถี่ ๆ บริเวณ Threshold:

ON
OFF
ON
OFF

28.11 Commanded State

Gateway ส่งคำสั่ง ON ไปยัง pkru/iot/001/cmd แต่การส่งคำสั่งไม่ได้ยืนยันว่า Actuator เปลี่ยนสถานะแล้ว:

Command Sent
    ≠
Actuator Changed

ดังนั้น ESP32 ต้องรายงาน Actual State เช่น ON กลับมาที่ pkru/iot/001/state

28.18 SQL Query

คุณต้องสามารถ Query ข้อมูลล่าสุด, ข้อมูลย้อนหลัง และค่าสถิติ AVG, MIN, MAX ตัวอย่าง:

SELECT
    device_id,
    AVG(temp),
    MIN(temp),
    MAX(temp)
FROM sensor_data
WHERE timestamp >= datetime(
    'now',
    '-5 minutes'
)
GROUP BY device_id;

28.21 Rule & Alert

ระบบต้องมีสถานะอย่างน้อย NORMAL, WARNING และ ALERT

เงื่อนไข สถานะ
temp < 30 NORMAL
30 ≤ temp ≤ 35 WARNING
temp > 35 ALERT

28.22 Alert ไม่เท่ากับ Control

ALERT คือสถานะที่ระบบตีความจากข้อมูล Sensor ส่วน ON/OFF คือคำสั่งควบคุม Actuator ทั้งสองอย่างจึงไม่ใช่เหตุการณ์เดียวกัน

ตัวอย่างเมื่อ temp = 38 ระบบประเมินสถานะเป็น ALERT:

Control Mode การทำงาน
AUTO ระบบส่งคำสั่ง Fan → ON ตาม Rule ที่กำหนด
MANUAL ระบบแสดง ALERT แต่รอให้ User เป็นผู้สั่ง ON/OFF

28.23 Python Gateway

อย่างน้อยหนึ่งส่วนของ Processing ต้องพัฒนาด้วย Python บน Raspberry Pi ตัวอย่างงานที่เหมาะกับ Python ได้แก่:

  • MQTT Subscribe
  • JSON Parsing และ Validation
  • Device Identification
  • Rule Processing และ Automatic Control
  • Health Monitoring

Node-RED สามารถรับผิดชอบ Dashboard, Visualization และ Manual Control

28.24 Control Authority

ไม่ควรให้ Python และ Node-RED สร้าง Automatic Control Command พร้อมกันโดยไม่มีการกำหนดเจ้าของการตัดสินใจ ต้องระบุ Control Authority ให้ชัดเจน ตัวอย่าง:

Python
    → Automatic Control
Node-RED
    → Dashboard
    → Manual Control

28.25 Gateway Protocol

ระดับพื้นฐานใช้ MQTT เป็น Protocol หลัก กลุ่มที่ต้องการเพิ่มความสามารถสามารถใช้ BLE/BTHome หรือ UDP ร่วมกับ Architecture ต่อไปนี้:

BLE ─┐
UDP ─┼→ Raspberry Pi → MQTT
MQTT ┘

แต่ไม่บังคับให้ทุกกลุ่มต้องใช้ทุก Protocol

28.28 MQTT Security

Mosquitto ใน Final Project ต้องใช้ Username, Password และ ACL และต้องไม่ตั้ง allow_anonymous true

28.29 ACL

Device ต้องเข้าถึงเฉพาะ Topic ที่จำเป็น โดย sensor001 มีสิทธิ์ดังนี้:

สิทธิ์ Topic
Write pkru/iot/001/data
Write pkru/iot/001/status
Write pkru/iot/001/state
Read pkru/iot/001/cmd

ตัวอย่าง Mosquitto ACL:

user sensor001
topic write pkru/iot/001/data
topic write pkru/iot/001/status
topic write pkru/iot/001/state
topic read pkru/iot/001/cmd

เมื่อไม่ได้กำหนดสิทธิ์ข้ามอุปกรณ์ sensor001 ต้องไม่สามารถ Publish ไปยัง pkru/iot/002/data หรือ Topic ของ Device อื่นได้

systemctl is-enabled iot-gateway

ผลลัพธ์ที่คาดหวังคือ enabled

28.34 Fault Tolerance

ระบบต้องรับมือ Failure อย่างน้อยดังนี้:

  • Invalid Sensor Data
  • Stale Data
  • Device Offline
  • Python Process Crash
  • MQTT Disconnect
  • Internet Failure
  • Remote Destination Failure
  • Raspberry Pi Reboot

28.35 Failsafe

คุณต้องกำหนด Failsafe Policy ให้เหมาะกับ Physical System ตัวอย่างเมื่อ Temperature Sensor เป็น STALE ต้องเลือกและอธิบายเหตุผลว่าจะให้ Fan:

  • ON
  • OFF
  • KEEP LAST STATE
  • เข้า SAFE MODE

28.36 Backup

Backup ต้องครอบคลุมอย่างน้อย:

  • Mosquitto configuration
  • Node-RED flows และ settings
  • Python source code และ dependencies
  • SQLite database
  • systemd service files
  • manifest หรือรายการไฟล์ที่สำรอง

28.37 Recovery

ไม่จำเป็นต้องทำลายระบบจริง แต่ต้องอธิบายและสาธิตกระบวนการต่อไปนี้อย่างน้อยหนึ่งส่วน:

  ↓

  ↓

  ↓

28.38 Gateway Health

แนะนำให้ Gateway รายงาน Health ที่ Topic pkru/gateway/status ตัวอย่างเมื่อทุกส่วนทำงานปกติ:

{
  "status":"HEALTHY",
  "mqtt":true,
  "database":true,
  "internet":true
}

เมื่อ Internet หาย

{
  "status":"DEGRADED",
  "mqtt":true,
  "database":true,
  "internet":false
}

28.39 Gateway State

Gateway ต้องรายงานสถานะอย่างน้อย 3 ระดับ:

State ความหมาย
HEALTHY Critical Components ทำงานปกติ
DEGRADED บาง Function ใช้งานไม่ได้ แต่ Essential Local Operation ยังทำงาน
FAILED Essential Operation ไม่สามารถทำงานได้

28.40 Fault Injection Test

คุณต้องจงใจสร้าง Failure เพื่อพิสูจน์ระบบอย่างน้อย 6 กรณี:

  1. ส่ง Invalid Sensor Data
  2. หยุด Device
  3. Kill Python Process
  4. หยุด Mosquitto
  5. ตัด Internet
  6. Reboot Raspberry Pi

28.41 Test 1 - Invalid Data

ส่ง

mosquitto_pub \
-h localhost \
-t "pkru/iot/001/data" \
-m '{"temp":-99,"humi":70,"light":1500}'

ผลที่คาดหวัง:

  • ข้อมูลถูกจัดสถานะเป็น INVALID
  • ข้อมูลไม่ถูกส่งเข้าสู่ Automatic Control ตามเส้นทางปกติ

28.42 Test 2 - Device Offline

หยุด ESP32 หรือ Simulator ผลที่คาดหวัง:

ONLINE
  ↓
OFFLINE

Device อื่นต้องยังทำงานต่อได้

28.43 Test 3 - Python Crash

หา PID

pid=$(systemctl show \
-p MainPID \
--value \
iot-gateway)

Kill

sudo kill -9 "$pid"

Expected

systemd
  ↓
Restart
  ↓
MQTT Reconnect
  ↓
System Resume

28.44 Test 4 - MQTT Failure

หยุด Broker

sudo systemctl stop mosquitto

ผลที่คาดหวังคือ Gateway ตรวจพบการตัดการเชื่อมต่อ จากนั้นเปิด Broker กลับ:

sudo systemctl start mosquitto

หลัง Broker กลับมา ระบบต้อง:

Reconnect
  ↓
Subscribe
  ↓
Resume

28.45 Test 5 - Internet Failure

ตัด Internet Upstream โดยไม่ปิด Local Network แล้วตรวจสอบผลดังนี้:

ส่วนประกอบ ผลที่คาดหวัง
Remote Access ใช้งานไม่ได้
Remote Upload ใช้งานไม่ได้
Local MQTT ยังทำงาน
Local Dashboard ยังทำงาน
SQLite ยังทำงาน
Automatic Control ยังทำงาน

ข้อมูลที่ยังส่งไปยัง Remote Destination ไม่สำเร็จต้องมีสถานะ PENDING

28.46 Test 6 - Reboot

sudo reboot

หลัง Boot ตรวจ

systemctl is-active mosquitto
systemctl is-active iot-gateway
systemctl is-active nodered

ผลที่คาดหวังคือระบบกลับมาทำงานโดยไม่ต้อง Run Python ด้วยมือ

28.47 Test 7 - Store-and-Forward

ถ้ามี Remote Destination ให้หยุดปลายทางชั่วคราว จำนวนรายการ PENDING ต้องเพิ่มขึ้น เมื่อเปิดปลายทางอีกครั้ง สถานะต้องเปลี่ยนดังนี้:

PENDING
  ↓
SENT

28.48 Test 8 - Malformed JSON

mosquitto_pub \
-h localhost \
-t "pkru/iot/001/data" \
-m 'HELLO'

ผลที่คาดหวัง:

  • Reject payload
  • บันทึก Error ลง Log
  • Gateway ทำงานต่อโดยไม่ Crash

28.49 Test 9 - ACL

ใช้ Account ของ Device 001 พยายาม Publish ไปยัง pkru/iot/002/data ผลที่คาดหวังคือ DENIED

28.50 Test 10 - Command Verification

ส่งคำสั่ง ON แล้วตรวจ pkru/iot/001/state ผลที่คาดหวังคือ ON หาก Commanded State กับ Actual State ไม่ตรงกัน ระบบต้องแสดงความผิดปกติได้

28.51 Fault Test Matrix
